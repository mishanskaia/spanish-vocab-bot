# CLAUDE.md — Руководство для нового ИИ-разработчика

Этот файл написан так, чтобы ИИ без какого-либо предыдущего контекста мог продолжить разработку.
Читай внимательно: здесь объясняется не только ЧТО сделано, но и ПОЧЕМУ.

---

## Что это за проект

Telegram-бот для изучения испанского языка с нуля. Пользователь — русскоязычный, уровень A1-A2.
Бот хранит словарный запас и повторяет слова по кривой интервальных повторений.

Это самостоятельный проект. Существует также похожий английский бот (`../vocab_bot/`) —
он послужил архитектурной основой, но это разные боты с разными БД и разными токенами.

## Как запустить локально

```bash
pip install -r requirements.txt
# создай .env на основе .env.example, заполни токены
python bot.py
```

Переменные окружения:
```

API_KEY=...                 # секрет для чтения через API (см. раздел «API» ниже); не задан — чтение отключено
API_WRITE_KEY=...           # секрет для добавления слов через API; не задан — запись отключена
OWNER_TELEGRAM_ID=...       # твой telegram user_id (узнать через @userinfobot) — без недельного лимита на новые слова

OPENAI_API_KEY=...          # распознавание и озвучка (вечерняя практика, голосовой ввод, /talk); не задан — всё это выключено

                              # пользователям («спроси автора»); не задан — сообщение без ссылки на ник
PUBLIC_BASE_URL=...         # адрес для /talk; не задан — берётся RAILWAY_PUBLIC_DOMAIN (Railway ставит сам)
TALK_LLM_MODEL=...          # модель Claude для живого разговора; не задан — claude-sonnet-4-6
```

## API

Отдельный внешний сайт может читать и добавлять слова пользователя через HTTP — например,
дашборд или форма для быстрого добавления слов, которые потом учатся в Telegram как обычно.
Сервер поднимается прямо внутри `bot.py`, в том же процессе и контейнере, что и сам Telegram-бот
(через `aiohttp`, запускается в `post_init` рядом с polling'ом — не отдельный Railway-сервис).
Запись безопасна из того же процесса — конфликтов параллельной записи, как между разными
процессами/сервисами, тут нет.

```
GET  /words?user_id=<telegram_user_id>&key=<API_KEY>
POST /words   {"user_id": <telegram_user_id>, "word": "aburrido", "key": "<API_WRITE_KEY>"}
GET  /health  # без авторизации, просто проверка что процесс жив
```

- `GET /words` — читает список слов. Без `API_KEY` в переменных окружения — всегда отвечает 401
  (сознательно).
- `POST /words` — принимает только само слово/фразу; перевод, примеры, спряжение и т.п. генерирует
  Claude через `ai_helper.explain_word()` — точно так же, как при обычном сообщении боту напрямую.
  Сохраняет через `db.add_word()`, так что дедуп по фразе (без учёта регистра) работает так же, как
  и в Telegram — повторная отправка того же слова не создаёт дубль, просто вернёт существующее.
  Без `API_WRITE_KEY` в переменных окружения — всегда отвечает 401.
- **Читающий и пишущий ключ — разные** (`API_KEY` и `API_WRITE_KEY`), сознательно: read-ключ можно
  отдать куда-то для просмотра (например, публичному дашборду), не давая тем самым право писать.
- Если понадобится доступ с другого процесса/сервиса (не из этого же контейнера) — вот тогда стоит
  мигрировать на Postgres, SQLite не для параллельной записи из разных процессов.
- Чтобы сайт был доступен снаружи — нужно включить публичный домен для сервиса в Railway
  (Settings → Networking → Generate Domain, порт 8080). Без этого сервис слушает порт, но наружу
  не торчит.
- CORS открыт (`Access-Control-Allow-Origin: *`) — авторизация целиком на `key`, так что это ок для
  персональных данных за секретным ключом, но не делай так для чего-то чувствительнее.

## Архитектура: пять файлов + страница

(До 2026-09-15 было три — `stt_helper.py` добавлен для вечерней практики; 2026-09-19 — `voice_talk.py` и `static/talk.html` для живого разговора, см. ниже.)

### `bot.py` — всё что связано с Telegram
Хендлеры команд, кнопок, сообщений. Логика отображения карточек повторения.
Состояние очередей хранится в `context.user_data` — **эфемерно**, теряется при рестарте бота.

### `db.py` — вся работа с SQLite
Схема таблицы, CRUD, логика интервалов, определение окна суток, пулы overdue/scheduled.
**Не держи бизнес-логику интервалов в bot.py** — всё в db.py.

### `ai_helper.py` — промпты к Claude Sonnet 4.6
- `explain_word(word)` — объяснить одно слово

Claude отвечает только JSON. Парсинг в `_ask_claude()` — стрипает markdown-обёртку если есть.

**Двунаправленный ввод — испанский или русский, добавлено 2026-09-14.** `explain_word()` принимает
любой текст без предварительной проверки, на каком языке он написан — направление определяет сама
модель, по инструкции внутри промпта ("это может быть слово на испанском ИЛИ на русском — если
русское, сначала подбери самый частотный испанский перевод для A1-A2 и дальше объясняй именно его").
Никакой Python-детекции языка нет специально — не нужна: один и тот же вызов Claude уже делает всю
работу, добавлять эвристику (например, проверку на кириллицу) означало бы дублировать то, что модель
и так должна уметь. `phrase` в ответе — всегда испанское слово/фраза, независимо от языка ввода, так
что вся остальная логика (дедуп по `phrase`, карточки повторения, инварианты БД) не меняется вообще.
Из этого следует та же частичная природа дедуп-check до вызова Claude (см. «Недельный лимит на новые
слова» выше): если пользователь уже добавил "hola" через испанский ввод, а потом наберёт "привет" —
предварительная проверка (`find_word_by_phrase` на сыром вводе) её не поймает, поймает только
`add_word()` постфактум, когда Claude уже вернёт каноническое "hola" — то есть один лишний вызов
Claude на такой конкретный сценарий всё равно уйдёт, тот же компромисс, что и раньше.

Функции в `ai_helper.py` — синхронные (обычный `Anthropic()`-клиент, блокирующий HTTP-вызов), а весь
бот — один asyncio event loop (Telegram polling, три джобы-напоминания и aiohttp API живут в нём же).
**Каждый вызов `explain_word()`/`get_mnemonic()` из `bot.py` ОБЯЗАТЕЛЬНО через
`await asyncio.to_thread(...)`** — иначе на время вызова (5–30 сек, задокументировано ниже) блокируется
вообще всё: сообщения других пользователей, напоминания, HTTP API. С одним пользователем это незаметно,
с несколькими — бот встаёт колом на всех сразу. Найдено и исправлено 2026-09-06 при подготовке к раздаче
бота другим людям — если добавишь новый вызов Claude из хендлера, не забудь `to_thread`.

### `stt_helper.py` — распознавание речи (OpenAI)
`transcribe(audio_bytes)` — голосовое → дословный текст. Отдельный файл и отдельный провайдер, потому
что Claude API аудио не принимает (проверено по документации 2026-09-15). Клиент создаётся лениво:
без `OPENAI_API_KEY` бот стартует как обычно, просто вечерняя практика выключена
(`EVENING_PRACTICE_ENABLED` в `bot.py`). Вызов — тоже только через `asyncio.to_thread`.

### `voice_talk.py` + `static/talk.html` — живой разговор голосом
Mini App и серверные маршруты `/talk*` на том же aiohttp-сервере. Подробности — раздел
«Живой разговор голосом» ниже.

## Схема БД (таблица `words`)

```sql
id, user_id, phrase, meaning, part_of_speech, cefr_level,
examples (JSON-массив строк, 3 штуки),
collocations (JSON-массив строк "фраза — перевод", 2-4 штуки или []),
conjugation (строка или NULL, только для глаголов),
gerund (строка герундия или NULL, только для глаголов),
added_date, interval_stage (0–6), next_review_date,
correct_streak, status, times_reviewed, success_rate, last_reviewed,
pool ('scheduled'|'overdue'),
added_window ('morning'|'evening')
```

**Важные инварианты:**
- Существительные в `phrase` — всегда с артиклем: `la casa`, `el coche`. Это требование к промпту.
- Глаголы в `phrase` — инфинитив: `hablar`, `ser`. Спряжение отдельно в `conjugation`.
- `examples` — JSON-массив, хранится как TEXT. При чтении всегда `json.loads(row["examples"] or "[]")`.
  Каждая строка — `"испанское предложение — русский перевод"` в одной строке через " — " (см. промпт
  в `ai_helper.py`). Это load-bearing формат: карточки повторения парсят его через `_split_example()`
  в `bot.py`, чтобы показать русский перевод как контекст, когда не получилось сделать пропуск.
- **Целое предложение на входе** (с 2026-09-15, чаще всего при голосовом вводе): карточка делается на
  ключевое слово предложения, а само предложение пользователя (естественный испанский вариант — его
  исходная русская фраза) идёт **первым** примером. Так карточка остаётся словарной (дедуп, пропуски,
  спряжение не меняются), но слово привязано к тому, что человек сам хотел сказать. Первый пример —
  тот, из которого `_build_recall_prompt()` делает пропуск, поэтому промпт просит ставить ключевое слово
  в той же форме, что и в `phrase`. Короткие устойчивые выражения («оплатить картой») остаются
  выражениями. Появилось после «Я бы хотела заправиться» → голый *repostar* без исходной фразы.
- `status = 'skipped'` — легаси-статус от удалённой команды /words (см. ниже); новые строки с этим
  статусом больше не создаются, но старые могут остаться в БД у пользователей, у кого /words был
  в ходу. Не участвует в повторениях — исключён во всех запросах `status NOT IN ('mastered', 'skipped')`.
- `pool = 'overdue'` — слово не было повторено в срок. Устанавливается в `detect_and_mark_overdue()`.

## Логика интервальных повторений

```python
INTERVALS = [1, 3, 7, 14, 30, 90]  # дней, 6 ступеней
```

**Первое повторение** — в тот же день или на следующий, зависит от окна суток (МСК):
- Утро (6–14): `next_review_date = сегодня`, `added_window = 'morning'`
- Вечер (14–23) или ночь: `next_review_date = завтра`, `added_window = 'evening'`

**Оценка при повторении** (`mark_review_result(word_id, grade)`), три градации:
- `'remember'` (🟢 Помню): `stage += 1`, дней = `INTERVALS[stage]`
- `'almost'` (🟡 Почти помню): `stage` не меняется, дней = `max(1, round(INTERVALS[stage] * 0.8))`
- `'hard'` (🔴 Сложно): `stage` не меняется, дней = `max(1, floor(INTERVALS[stage] * 0.6))`

`'almost'` добавлена 2026-09-02 как средняя градация между «вспомнил» и «не вспомнил» — раньше
self-grade был бинарным, и пограничные случаи (слово узнал, но не сразу/не уверенно) приходилось
искусственно относить к одной из двух крайностей. **Не путать со старым `'easy'`**: третий grade уже
был раньше — сидел НАД `'remember'` (ускоренный интервал `*1.3` для "слишком легко") и его убрали,
судя по всему потому что учащиеся склонны переоценивать лёгкость и разгонять интервал быстрее, чем
слово реально закрепилось. `'almost'` сидит НИЖЕ `'remember'`, между ним и `'hard'`, и намеренно НЕ
продвигает `stage` — только смягчает интервал по сравнению с `'hard'`. Если будешь трогать эту логику
ещё раз, не давай `'almost'` продвигать `stage` — это и есть грабли из старого `'easy'`.

Мнемоника (`_maybe_ask_mnemonic`) теперь предлагается при любом grade кроме `'remember'` — то есть и на
`'almost'`, и на `'hard'` (раньше — только на `'hard'`).

Кнопка «Другой вариант 🔄» (`mnemo_retry`, `bot.py`) — Claude-вызов без даты добавления слова, поэтому
не попадает под недельный лимит новых слов. Ограничена отдельно: `MNEMONIC_RETRY_LIMIT = 3` попытки на
слово (столбец `mnemonic_retries` в БД), `OWNER_TELEGRAM_ID` — без лимита. При исчерпании лимита кнопка
`mnemo_retry` пропадает из клавиатуры (`_mnemonic_keyboard(word_id, show_retry=False)`), остаётся только
«Оставить». Добавлено 2026-09-06 вместе с остальной подготовкой к раздаче бота — до этого retry был
не ограничен вообще.

После stage 5 (последнего) → `status = 'mastered'`.

**Overdue:** если `next_review_date < сегодня` и `pool = 'scheduled'` → `pool = 'overdue'`, `stage -= 1`.
Вызывается в `detect_and_mark_overdue(user_id)` при старте каждой сессии /review.

## Пользовательский флоу

### Добавление слова
Пользователь пишет любой текст (не команду) → `handle_message()` → Claude → сохранить в БД.
**Нет команды /add** — это сознательное решение для простоты UX. Не добавляй /add без нужды.

### /words (удалена 2026-09-06)
Раньше подбирала 5 новых слов через `ai_helper.find_frequent_words()` — Claude получал список ВСЕХ
слов пользователя и предлагал следующую порцию, показывались по одному с кнопками Сохранить/Пропустить,
пропущенные сохранялись в БД со статусом `skipped`. Убрана как ненужная на момент раздачи бота другим
пользователям — точка входа, ради которой в первую очередь понадобился дневной лимит на новые слова
(см. ниже), автор планирует заменить её на что-то другое позже. `find_frequent_words()` и
`db.add_skipped_word()` удалены вместе с командой; статус `skipped` в схеме и в фильтрах остался
(см. «Важные инварианты» выше) — новые такие строки просто больше не появляются.

### Недельный лимит на новые слова

Каждое новое слово (через обычное сообщение или API `POST /words`) — это вызов Claude, который стоит
денег с личного `ANTHROPIC_API_KEY` владельца бота (~1 цент/слово на `claude-sonnet-4-6`). Добавлено
2026-09-06 как дневной лимит (когда бот стали давать другим пользователям), переведено на недельный
2026-09-13 (сессия `/grill-me`) — та же логика "5 слов/день", но раз в неделю, а не каждый день:
даёт человеку гибкость распределить слова неровно (например, 10 в выходные, 0 в будни), не увеличивая
общий бюджет токенов на пользователя.

`_weekly_limit_reached(user_id)` в `bot.py` — если `user_id == OWNER_TELEGRAM_ID`, лимита нет; иначе
сравнивает `db.count_words_added_this_week(user_id)` с `WEEKLY_NEW_WORD_LIMIT` (по умолчанию 35 = 5×7).
Проверка стоит **до** вызова Claude в обеих точках входа — `handle_message()` и `handle_api_add_word()`
— чтобы при исчерпанном лимите токены вообще не тратились.

**Календарная неделя, не скользящее окно** — сознательный выбор (обсуждали оба варианта в сессии
`/grill-me`): лимит сбрасывается по понедельникам в **локальном времени пользователя**
(`db._local_week_start()`, использует тот же `utc_offset_hours`, что и часовой пояс реминдеров — см.
«Часовой пояс пользователя» ниже), а не "последние 7 дней от сегодня". Проще объяснить человеку
("на этой неделе осталось N"), хотя ценой этого — можно выжать все 35 слов сразу в первый день после
сброса.

`count_words_added_this_week()` считает строки в БД с `added_date >= понедельник этой недели`
**независимо от статуса** (включая `skipped`) — потому что Claude уже был вызван к моменту, когда
стало известно, дубль это или нет (лимит про потраченные токены, а не про итоговый размер словаря).
`added_date` — ISO-строка, поэтому сравнение `>=` с датой понедельника работает как обычное
лексикографическое сравнение, без парсинга дат в SQL.

**Дубль-check до вызова Claude.** До 2026-09-12 повторная отправка уже добавленного слова всё равно
дёргала Claude (дедуп по фразе происходил только внутри `db.add_word()`, уже после вызова) — реальная
дыра при раздаче бота знакомым: кто-то мог случайно или специально заспамить одно и то же уже
известное слово сколько угодно раз в день, и каждый раз это стоило денег, а дневной лимит этого не
видел вообще (новая строка не создавалась). Разобрано в сессии `/grill-me` 2026-09-12. Исправлено:
`handle_message()` и `handle_api_add_word()` теперь сначала зовут `db.find_word_by_phrase(user_id, word)`
на сыром введённом тексте — если фраза уже есть **в точности как её ввели** (case-insensitive), отвечают
«уже есть» без вызова Claude вообще. Это частичный фикс, не полный: `find_word_by_phrase` матчит только
точную форму ввода, так что не ловит вариант, когда пользователь вводит слово в другой форме, чем оно
хранится (например, "casa" при уже сохранённом "la casa" — Claude канонизирует существительные с
артиклем, а до вызова Claude мы не знаем канонической формы). Такие случаи по-прежнему словятся только
постфактум — внутри `db.add_word()` через `is_new=False` — и один вызов Claude на них всё равно уходит.
Для основного сценария злоупотребления (повторная отправка того же текста) фикса достаточно; полный
фикс (считать сами попытки вызова Claude, а не добавленные строки) отложен как избыточный для
маленького круга доверенных тестировщиков.

### /review
1. Очищает `context.user_data["review_shown"]` (set ID уже показанных в этой сессии)
2. Вызывает `detect_and_mark_overdue()`
3. Отправляет `RECALL_DISCLAIMER` один раз в начале сессии (напоминание, что ответ — в словарной форме)
4. Показывает overdue-слова первыми (с ⚠️), потом scheduled
5. Все карточки — активное воспоминание, self-graded (см. «Типы карточек» ниже)

### /all
Повторить все слова из базы в случайном порядке, без учёта расписания.
Использует отдельную очередь `context.user_data["all_queue"]`.
После grade — переходит к следующему в очереди, не перезапрашивает БД.

## Типы карточек при повторении

Раньше было два формата — recognition (перевод → вспомни слово) и fill-in-the-blank
multiple choice (пропуск в предложении + 3 кнопки-варианта). MC убрали: узнавание среди
готовых вариантов не задействует активное воспоминание так, как задействует свободное
воспроизведение (testing effect). Теперь один формат — активное воспоминание с контекстом,
всегда self-graded (кнопка «Показать ответ» → три кнопки оценки Помню 🟢 / Почти помню 🟡 / Сложно 🔴,
см. «Логика интервальных повторений» выше).
Ответ всегда показывается в словарной форме (`row["phrase"]`) — инфинитив для глаголов,
с артиклем для существительных — даже если в примере слово стоит в другой форме. Отсюда
`RECALL_DISCLAIMER`, который бот один раз показывает в начале сессии /review и /all.

Логика в `_build_recall_prompt()` (`bot.py`), три уровня по убыванию:

1. **Пропуск в предложении.** Берёт первый пример из `examples`, ищет испанскую часть слова
   (без артикля для существительных) в испанской половине примера (`_split_example()`),
   заменяет на `_____`. Показывает пропуск вместе с русским переводом предложения.
2. **Контекст без пропуска.** Если слово не нашлось в тексте (частая причина — глагол в
   примере стоит в спряжённой форме, а не в инфинитиве) — показывает русский перевод
   предложения как подсказку-контекст плюс явный вопрос "Как будет по-испански: {meaning}".
3. **Голый перевод.** Если у слова вообще нет примеров или строка не содержит `" — "` —
   fallback на самый простой формат: "Как будет по-испански: {meaning}".

Функция `_make_blank()` делает точный поиск подстроки, не морфологический — для глаголов
попадает в уровень 1 редко (только если в примере случайно тот же инфинитив), обычно
уходит на уровень 2. Это ожидаемо и нормально, а не баг.

## Уведомления и лимит на сессию

- **10:00 / 14:00 / 18:00 — в локальном времени каждого пользователя** (не всегда МСК, см. «Часовой
  пояс пользователя» ниже). Одна джоба `hourly_reminder_job()` (`bot.py`), `run_repeating` раз в час:
  для каждого due-пользователя переводит текущий UTC-час в его локальный через сохранённое смещение
  и проверяет совпадение с одним из трёх слотов (`REMINDER_LOCAL_SLOTS`). Три сессии в день вместо
  одной — добавлено 2026-09-03: при большом бэклоге (сто и больше слов) одна сессия утром пугает и
  отбивает желание открывать бота вообще; исследование (spacing effect, Anki/SuperMemo best practices)
  подтверждает, что несколько сессий по 20-30 карточек лучше для запоминания, чем одна массированная.
- `SESSION_WORD_LIMIT = 30` — жёсткий лимит слов за одну сессию (не только новых — вообще всех
  показанных карточек). Считается по `len(review_shown)` в `_send_next_due()`. При достижении —
  сообщение "На эту сессию хватит" вместо карточки; остаток ждёт следующей сессии, каждая сессия
  (реминдер или ручной `/review`) сбрасывает `review_shown` и даёт свежие 30.
- Реминдер отправляется только если есть слова, не повторённые сегодня (`count_due_not_reviewed_today()`).
  Текст показывает `min(count, 30)` как «слов на эту сессию», и только если реальный бэклог больше —
  тихой строкой ниже «всего в очереди: N» — чтобы не пугать полным числом каждый раз.
- После уведомления сразу начинается сессия повторения.
- **Итог сессии** (добавлено 2026-09-19): если в сессии `/review` показано больше
  `SESSION_SUMMARY_MIN_WORDS = 20` карточек, в конце (очередь кончилась или упёрлись в лимит 30)
  `_maybe_send_session_summary()` шлёт одно короткое сообщение «слово — перевод» по словам с оценкой
  «Сложно» и «Почти помню». Оценки копятся в `user_data["review_grades"]` (сбрасывается вместе с
  `review_shown`, эфемерно как и он). «Помню» в итог не входит; если сложных не было — сообщения нет;
  на `/all` итога нет.

## Часовой пояс пользователя

Добавлено 2026-09-12 (сессия `/grill-me`) вместе с раздачей бота знакомым — раньше все реминдеры были
жёстко на МСК, что имело смысл, пока ботом пользовалась только Ольга, но ломается, если тестировщик
живёт в другом поясе (реминдер в 10:00 МСК может оказаться серединой ночи).

**Выбранный вариант — только смещение, не полная кастомизация времени** (рассматривались более тяжёлые
варианты: одно время на пользователя вместо трёх слотов, или три индивидуальных времени — отклонены
как избыточные для теста на 5 знакомых; полная кастомизация — на будущее, если понадобится).

- При первом `/start`, если `db.get_user_utc_offset(user_id) is None` — бот вместо приветствия
  спрашивает "который у тебя сейчас час" и ставит `context.user_data["awaiting_tz_reply"] = True`.
  Следующее текстовое сообщение перехватывается в начале `handle_message()` и уходит в
  `_handle_tz_reply()` вместо обработки как нового слова.
- Парсинг — `_TZ_REPLY_RE`, формат `HH`, `HH:MM`, `HH.MM` или `HH,MM`. Смещение считается как разница
  между указанным локальным временем и текущим UTC, округлённая до целого часа, с нормализацией через
  полночь (`((diff + 720) % 1440) - 720`). **Точность — только целый час**, без DST и получасовых
  поясов (Индия, Непал и т.п.) — осознанное упрощение, достаточное для задачи "не разбудить реминдером
  среди ночи", не претендует на точность часового пояса.
- `db.set_user_utc_offset()` / `db.get_user_utc_offset()` — таблица `user_settings` (`user_id`
  PRIMARY KEY, `utc_offset_hours`). Тот, кто ещё не ответил (включая старых пользователей до этой
  фичи) — `None`, и вызывающий код (`hourly_reminder_job`) подставляет `DEFAULT_UTC_OFFSET = 3`
  (Москва) — то есть для всех, кто не ответил, поведение не меняется вообще.
- **Почасовой polling вместо динамических джоб на пользователя** — `hourly_reminder_job()` идёт по
  всем due-пользователям каждый час и сверяет их локальный час с `REMINDER_LOCAL_SLOTS = {10, 14, 18}`.
  Так как смещения только целочасовые, а джоба идёт раз в час — совпадение слота случается максимум
  один раз в сутки, дублей нет. Выбрано вместо создания/удаления индивидуальных `run_daily`-джоб на
  каждого пользователя при смене смещения — заметно проще для маленького круга пользователей, хотя и
  менее точно по минутам (реминдер может прийти не ровно в :00, а в любую минуту часа, когда джоба
  фактически стартовала — не критично для задачи).
- Study Coach (`study_coach_reminder`) **не тронут** — он владельцу и только владельцу, остаётся на
  фиксированном МСК-времени, как и раньше.
- `db.get_current_window(utc_offset_hours=3)` — тоже переведена на смещение (раньше жёстко звала
  `get_moscow_now()`). Это влияет на текст-подсказку при добавлении нового слова ("Первое повторение —
  сегодня вечером" / "завтра утром") — `db.add_word()` сама подставляет смещение добавившего слово
  пользователя, `handle_message()` — то же самое смещение для текста подсказки. Без этого у человека
  из другого пояса "утро/вечер" считались бы по Москве, а не по нему самому — заметили и поправили в
  той же сессии `/grill-me`, а не оставили как отдельное ограничение.

**Найдено при финальной проверке 2026-09-13, перед первой реальной раздачей:**
- Одно место всё ещё показывало захардкоженное "10:00 / 14:00 / 18:00 МСК" — сообщение о достижении
  `SESSION_WORD_LIMIT` внутри `/review` (`_send_next_due`). Поправлено на "по твоему времени", как
  везде остальные тексты.
- **Ловушка без выхода** в `_handle_tz_reply()` — если человек проигнорирует вопрос про время и
  попробует сразу прислать слово (или просто не поймёт формат), ответ не матчился `_TZ_REPLY_RE`, и
  бот отвечал "не поняла, напиши время цифрами" — **на любое** следующее сообщение, включая настоящие
  испанские слова, без способа выйти из этого состояния кроме как в итоге ответить числом. Добавлен
  `_TZ_SKIP_WORDS` — набор слов ("позже", "пропустить", "skip" и т.п.), которые снимают
  `awaiting_tz_reply` и оставляют смещение `None` (Москва по умолчанию, как если бы вопрос вообще не
  задавался), плюс упоминание этого способа прямо в сообщении об ошибке парсинга.

## Обработка ошибок

`error_handler()` в `bot.py`, зарегистрирован через `app.add_error_handler(error_handler)`. До
2026-09-06 необработанное исключение в любом хендлере просто уходило в лог Railway молча — пользователь
не получал вообще никакой реакции, а сама Ольга узнавала о баге, только если кто-то ей об этом написал.

Делает две вещи:
- Пользователю, у которого произошла ошибка (если есть `update.effective_chat`) — короткое «Что-то
  пошло не так, попробуй ещё раз» вместо тишины.
- `OWNER_TELEGRAM_ID` — личным сообщением от бота техническое сообщение (тип исключения + user_id),
  чтобы узнавать о багах у других пользователей не по их жалобам. Троттлинг
  `ERROR_NOTIFY_THROTTLE_SECONDS = 60` — если сломается что-то системное (например, протухнет
  `ANTHROPIC_API_KEY`) и ошибка посыплется у всех сразу, владелец получит одно уведомление в минуту,
  а не по одному на каждую попытку каждого пользователя. Пользовательское сообщение об ошибке
  троттлингу не подчиняется — ему реакция нужна на каждый его собственный сбой, вне зависимости от
  того, сколько уведомлений в это время получает владелец.

**Не пингует владельца на сетевые обрывы.** Добавлено 2026-09-13 — расследовали жалобу "бот шлёт мне
ошибки каждый день, хотя им ещё никто кроме меня не пользуется" (см. `/grill-me`, найдено через
`railway logs` по старым деплоям). Причины оказались две, обе не имеющие отношения к чужим
пользователям:
1. **Двойное нажатие «Показать ответ»** (`on_button`, action `"show"`) — второй `edit_message_text()`
   на уже изменённое сообщение падал с Telegram-ошибкой "message is not modified", раньше без
   try/except (в отличие от мнемоник, которые уже были обёрнуты). Обёрнуто, конкретно эта ошибка
   молча игнорируется — редкий двойной тап безвреден, второй раз просто нечего менять.
2. **Обрывы сети между Railway и Telegram** во время long-polling (`getUpdates`) — попадают в
   `error_handler` с `update=None` и исключением `telegram.error.NetworkError`, самовосстанавливаются
   на следующем поллинге, происходят с любым ботом на long-polling независимо от активности
   пользователей. `error_handler` теперь возвращается раньше троттлинга/уведомления владельца, если
   `isinstance(context.error, NetworkError)` — в лог всё равно попадает (`logger.error` выше по
   функции), просто без личного пинга.

## Доступ по инвайт-кодам

Добавлено 2026-09-12, когда решили пускать бота на нескольких знакомых (не близких друзей — доверия
"расскажу и так" нет) перед тем, как думать про рекламу/распространение. До этого allowlist'а не было
вообще — любой, кто узнал username бота, мог им пользоваться (в рамках дневного лимита слов). Разбор
решения — сессия `/grill-me` 2026-09-12, если понадобится восстановить ход рассуждений.

**Схема:** таблица `invites` (`db.py`) — `code`, `created_at`, `expires_at`, `used_by`, `used_at`.
- `/invite` (owner-only, `bot.py`) — генерирует случайный код (`secrets.token_urlsafe`), TTL
  `INVITE_TTL_DAYS = 15` дней, отдаёт готовую deep-link `https://t.me/<bot>?start=<код>`.
- Ссылка — не сам механизм защиты, а просто способ доставки: код одноразовый (`db.redeem_invite()`
  атомарно ставит `used_by` только если код ещё не погашен и не истёк), так что если ссылку переслали
  двоим — доступ получит первый, кто перешёл, остальные получат отказ тем же кодом.
- `expires_at` — **чистый housekeeping** (неиспользованный код перестаёт быть годным через 15 дней),
  а не механизм отслеживания «перешёл ли человек» — сознательно решили не делать отдельную
  команду/уведомление для этого (см. `/grill-me` сессию): узнаётся из обычного чекина с людьми, не
  через бота.
- `db.is_user_authorized(user_id)` — `True` навсегда, если этот `user_id` хоть раз что-то погасил
  (не привязано к судьбе самого кода после этого).
- **Гейт блокирует весь бот целиком**, не только добавление слов — `access_gate()` в `bot.py`,
  зарегистрирован в `group=-1` (раньше всех остальных хендлеров) и на любой апдейт от
  неавторизованного `user_id` отвечает `ACCESS_TEST_MESSAGE` + `ApplicationHandlerStop`, что не даёт
  апдейту дойти до хендлера в `group=0`. Единственное исключение — сообщение `/start`: пропускается
  без проверки, потому что сама `start()` разбирает код из `context.args` (deep-link `?start=код`
  Telegram передаёт как `/start код`) и либо гасит его, либо тоже отвечает `ACCESS_TEST_MESSAGE`.
- `OWNER_TELEGRAM_ID` — авторизован всегда через `_is_owner()`, инвайт не нужен (тот же принцип, что и
  у дневного лимита слов и `MNEMONIC_RETRY_LIMIT`).
- Модель доступа на случай будущей рекламы/массового распространения — сознательно не решена сейчас
  (см. TODO.md или `/grill-me` сессию 2026-09-12) — текущий гейт расcчитан на штучные приглашения от
  руки, не на самостоятельную регистрацию.

## Бэкапы

Добавлено 2026-09-12 (сессия `/grill-me`) — вся БД это один файл SQLite на Railway Persistent Volume,
без него бэкапов не было вообще: если volume повредится, все слова всех пользователей теряются
безвозвратно. Для теста на нескольких знакомых это не абстрактный риск, поэтому:

- `/backup` (owner-only, `bot.py`) — присылает Ольге в Telegram текущий файл БД как документ.
- Плюс тот же механизм еженедельно, автоматически — джоба в воскресенье 06:00 МСК (03:00 UTC,
  `BACKUP_WEEKLY_UTC` / `BACKUP_WEEKDAY`), тихое время перед дневными реминдерами.
- `db.create_backup(dest_path)` — использует `sqlite3.Connection.backup()` (SQLite backup API), а не
  копирование сырого файла. Это специально: простое копирование файла во время активной записи могло
  бы захватить недописанную страницу и дать битый файл; backup API отдаёт консистентный снапшот, даже
  пока бот в этот момент что-то пишет.
- Бэкап шлётся как временный файл (`tempfile.mktemp`), который удаляется сразу после отправки — не
  остаётся лежать на диске контейнера.

1. **Слот 1 — анкор дня ИЛИ due-тема грамматики.** Один слот, без стека (недельная сетка ниже).
2. **Слот 2 — 3 слова для активации в речи.** Показывается всегда, независимо от слота 1.
3. **Слот 3 — due-спикинг по теме**, если есть. Показывается всегда, независимо от слота 1.

### Недельная сетка (слот 1)

`STUDY_COACH_ANCHOR` (`bot.py`) — текст анкора по дню недели (`date.today().weekday()`, Пн=0):

| День | Слот 1 |
|------|--------|
| Пн (0) | ДЗ репетитора (анкор) |
| Вт (1) | ДЗ репетитора текстом + due-тема, если есть |
| Ср (2) | Аудирование (анкор) |
| Чт (3) | due-тема, если есть |
| Пт (4) | due-тема, если есть |
| Сб (5) | Чтение (анкор) |
| Вс (6) | due-тема, если есть |

Пн/Ср/Сб — анкор-only: due-тема грамматики туда никогда не попадает, даже если due, а просто ждёт
следующего дня из `STUDY_COACH_DUE_TOPIC_WEEKDAYS = (1, 3, 4, 6)`. Слот 3 (спикинг) в эту логику не
входит вообще — стреляет точно в свою дату независимо от дня недели, потому что живёт в отдельном
слоте того же сообщения, а не конкурирует со слотом 1 за анкор-дни.

### Грамматика — 5 чекпоинтов от даты входа X (таблица `study_topics`, `db.py`)

`/newtopic <тема>` — единая точка входа независимо от источника темы (ДЗ, самостоятельный дрилл,
видео). При вставке сразу считаются и фиксируются **все пять** дат: X+2, X+7, X+10, X+14, X+30.
**Даты никогда не пересчитываются** — это самое важное инвариант всей фичи. Если чекпоинт не может
быть показан сегодня (Пн/Ср/Сб для грамматики, или другая тема уже заняла слот) — дата в БД не
трогается, чекпоинт просто остаётся due (`{stage}_date <= today` и `{stage}_sent = 0`) и получит
слот при следующей проверке, где условия совпадут. Реализовано в `get_due_grammar_item()` /
`get_due_speaking_item()` — это чистые SELECT по уже сохранённым датам, никакого UPDATE дат.

- **X+2** — «Составь 10 предложений на тему {тема}»
- **X+7** — «Новый drills по {тема}»
- **X+14, X+30** — тот же принцип, третий и четвёртый подход
- **X+10** — отдельно, слот 3: «попробуй использовать {тема} в речи» (не грамматический дрилл,
  а нудж на использование в устной речи; выбрано намеренно НЕ синхронизировать с X+7/X+14, чтобы
  попадало между двумя дриллами)

Стадии проверяются **в хронологическом порядке per topic** (`GRAMMAR_STAGE_ORDER` в `db.py`) — если
тема сильно задержалась и её X+7 стал due уже после того, как технически подошла дата X+14, всё равно
сначала отдаётся X+7, а не перескакивает вперёд. Между темами при коллизии (несколько тем due в один
день) — выигрывает **самая старая по `added_date`**, остальные естественным образом ждут следующего
свободного дня тем же механизмом (без мутации дат, см. выше).

После X+30 — `status = 'done'`, тема навсегда уходит из активной очереди (`get_active_topics()`
фильтрует по `status = 'active'`). Очередь без жёсткого лимита на количество тем — по спеке
«обычно 1-3», но `/newtopic` не блокирует добавление сверх этого.

`/topics` — список активных тем с прогрессом по чекпоинтам. `/canceltopic <id>` — снять тему из
очереди (`status = 'cancelled'`) до завершения цикла, на случай опечатки или передумал(а).

Как и в остальной фиче — **никакого трекинга «выполнено/не выполнено»**: бот только присылает
напоминание, обратную связь по факту выполнения по-прежнему даёт репетитор.

### Слова для активации в речи (колонка `speech_activation_last_shown` в `words`)

Пул — `status IN ('familiar', 'active', 'mastered')` (stage ≥ 3, из вокаб-цикла повторений; не
путать с грамматическим циклом тем выше). Каждый день 3 слова с самым старым
`speech_activation_last_shown` (`get_speech_activation_words()`, `db.py`) — `NULL` (никогда не
показывалось) сортируется первым в SQLite при `ASC`, так что новые слова, только что дошедшие до
`familiar`, показываются раньше повторов. После показа — `speech_activation_last_shown` = сегодня.

Это даёт **вечную ротацию без отдельного флага «использовано» и без ручного сброса**: слово,
которое только что показали, перестаёт быть «самым старым» и естественно не всплывёт, пока не
покажутся все остальные слова пула. Изначально обсуждался вариант с 14-дневным окном исключения
(«не показывать то, что показывали за последние 2 недели») — отклонён в пользу этого механизма,
потому что окно по времени не гарантирует полное покрытие пула (часть слов могла годами не
попадаться при чисто случайном выборе с window-based исключением).

## Вечерняя практика (admin-only)

Добавлено 2026-09-15. Продуктивное владение: сказать вслух фразу с каждым из 3 слов, которые утром
прислал Study Coach (слот 2), и сразу получить разбор. Только `OWNER_TELEGRAM_ID`, как и Study Coach.
Требует `OPENAI_API_KEY`.

**Почему так, а не иначе** (обсуждение + `/llm-council` в той же сессии):
- **Отдельно от карточек по времени.** Совет рекомендовал встроить «составь предложение» прямо в
  `/review`. Отвергнуто реальным сценарием: карточки листаются на работе урывками и молча, а говорить
  вслух удобно только вечером дома.
- **Голосовые сообщения, а не real-time голос.** Решение 2026-08-30 «не конкурировать с real-time
  voice-AI» не нарушено.
- **Разговор на 6–8 реплик и скрытое наведение на слова через вопросы — отвергнуты** как слишком
  тяжёлые для A1 и натянутые. Одно слово = одна фраза + повтор с учётом правки.

**Флоу** (`bot.py`, секция «Evening practice»):
1. `hourly_reminder_job` → `_maybe_start_evening_practice()`: в `EVENING_PRACTICE_LOCAL_HOUR = 21` по
   времени владельца, если на эту локальную дату сессии ещё нет. `/practice` — то же самое вручную
   (для проверки); если утром слов не было, берёт следующие 3 из пула speech activation.
2. Карточка слова: русское значение + испанское под `<tg-spoiler>` (вспомнить слово — часть задания),
   кнопки «Дальше» / «Закончить». Сообщения практики — `parse_mode="HTML"` (спойлер в Markdown v1
   недоступен), весь динамический текст через `html.escape`.
3. `handle_practice_voice()` (`filters.VOICE`): голосовое → `stt_helper.transcribe` → бот показывает
   «🎧 Услышала: …» → `ai_helper.check_practice_phrase()` → ✅ верно (сразу следующее слово) / ✅ верно,
   но слишком просто (засчитано, предложено усложнить, слово не закрывается само) / 💡 ошибка
   (правильный вариант + «запиши ещё раз»). После `PRACTICE_MAX_ATTEMPTS = 3` — дальше без блокировки.
4. В конце (или по «Закончить») — итог: ✅ сразу / 🟡 после правки / 🔸 пока не получилось / ⏭ пропущено,
   с последней исправленной фразой под словами, где была правка.

**Инварианты и грабли:**
- **Состояние — в БД** (`practice_sessions`, `practice_attempts`), не в `context.user_data`: Railway
  перезапускает бот при деплое, сессия не должна обрываться. Одна сессия на локальную дату — это же
  защищает от повторной отправки после рестарта в 21:xx (в отличие от вокаб-реминдеров, см. P3 в TODO).
- **Флаг ожидания не нужен**: голосовые больше нигде в боте не используются, поэтому голосовое от
  владельца при активной сессии — всегда ответ практики. Не добавляй текстовый ответ без reply-to —
  он столкнётся с добавлением слов в `handle_message()`.
- Исход слова (`get_practice_word_outcome`) выводится из записанных попыток, а не хранится флагом.
- Нечёткая запись (`unclear`), пустой транскрипт и сбой STT попыткой не считаются.
- Пока идёт STT + Claude (секунды), можно успеть нажать «Дальше»: после разбора сессия перечитывается,
  и если слово уже закрыто — разбор показывается, но попытка не пишется.
- В `callback_data` кнопок есть индекс слова — двойное нажатие на старое сообщение не пропускает слово.

**Выбор STT — по реальным голосовым, `tests/stt_check.py`:** `gpt-4o-mini-transcribe` + промпт
«дословно» сохранил намеренные ошибки (*yo fue*, *el casa*) и русское слово посреди фразы. `whisper-1`
молча исправлял *fue*→*fui*; без промпта gpt-4o-модели *переводили* русское слово на испанский —
пробел в словаре исчезал. **Промпт обязателен.** Невнятно произнесённое слово модели угадывают по
контексту — как проверка произношения STT не годится, практика про грамматику и словарь.

**Промпт разбора (`check_practice_phrase`)** — главный риск тут ложные правки на A1. Правила: исправлять
только настоящие ошибки (верно, но можно иначе — не ошибка); огрехи транскрипции (пунктуация, значки
ударения) не комментировать; русское слово = пробел; целевое слово в любой форме; **пол говорящего
неизвестен** — «estoy cansado/cansada» оба верны (правило добавлено после того, как на живой проверке
модель «исправила» женский род на мужской). Если меняешь промпт — перепроверь на реальных фразах, в том
числе на заведомо верных.

Тест: `python tests/simulate_practice.py` (реальные `db.py`/`bot.py`, временная БД, STT и Claude —
заглушки).

## Живой разговор голосом (admin-only, 2026-09-19)

Разговор с ботом голосом без кнопок, с испанскими субтитрами. Бот вопросами наводит на слова из
базы. Только `OWNER_TELEGRAM_ID`.

**Почему пересмотрели решение 2026-08-30 «не конкурировать с real-time voice-AI».** Ольга платит за
сторонний Telegram-бот для разговорной практики (голосовое ↔ голосовое + правки, $50/год). У него три
недостатка: новые слова не попадают в её базу; цикл «записать → отправить → прослушать» не даёт
заниматься параллельно с делами; он не наводит на её слова. Решение 08-30 было про *продукт* против
стартапов с венчурными деньгами, а это личный инструмент вместо подписки. Звонок вместо Mini App
отвергнут: нужны субтитры (быструю испанскую речь на слух не успеть).

**История: сначала был OpenAI Realtime, в тот же день заменён.** Первая версия шла на
`gpt-realtime-2.1` по WebRTC. Технически заработала (5 минут, 4 из 10 целевых слов), но стоила
~$0.06/мин (~$25–30/мес при 15 мин в день, против ~$4/мес подписки). Ольга сказала, что живость
меньше секунды ей не нужна: проблема была в *кнопках*, а не в паузе перед ответом. Поэтому теперь
дешёвая цепочка из трёх шагов. **Не возвращайся к realtime ради скорости** без её запроса.

**Цепочка одного хода** (`voice_talk.handle_turn`):
1. Страница сама решает, что фраза, похоже, закончилась (см. паузы ниже), и шлёт WAV 16 кГц.
2. `stt_helper.transcribe_mixed` — та же модель, что в вечерней практике, но **без `language="es"`** и
   с промптом «испанский вперемешку с русским, русское — кириллицей». С `language="es"` (как в
   `transcribe()` для практики) модель писала русские слова латиницей («shapka») — найдено в третьей
   живой проверке. Локально промпт не проверить (OpenAI блокирует регион), поэтому Claude дополнительно
   понимает транслит как русский и в `translations.ru` пишет кириллицей.
3. `looks_unfinished()` — дешёвая проверка без LLM: фраза кончается на союз/предлог/артикль/«eh» →
   сразу «жду».
4. Параллельно два вызова Claude: `classify_complete` (Haiku 4.5, короткий промпт, `{complete}`) решает
   «договорила?», `claude_turn` (Sonnet 4.6, `{reply, translations}`) пишет ответ. Проверка сказала «не
   договорила» → сразу `wait`, ответ дописывается впустую. **Не возвращай решение «договорила?» в большой
   промпт разговора**: там Sonnet в 2 из 5 прогонов реальной цепочки считал законченную фразу («Mañana voy
   a la peluquería con mi hermana») незаконченной — бот молчал до 7 с и потом «помогал»; отдельный
   короткий промпт — 0 ошибок из 32 и на Sonnet, и на Haiku. Упала проверка → считаем «договорила».
5. `stt_helper.synthesize` (`gpt-4o-mini-tts`, голос marin, обычный темп) → mp3 в base64 → страница.

**Модель Claude — `claude-sonnet-4-6`** (переопределяется `TALK_LLM_MODEL`). Сравнивали на одних и тех
же репликах: Haiku 4.5 быстрее всех (~0.9 с), но делает ошибки в собственном испанском («la playa es
muy bonito», «yo también me encanta») — для собеседника-учителя недопустимо. Sonnet 5 медленнее
(1.5–4 с) и принимал законченные фразы за незаконченные. Sonnet 4.6 — все решения «договорила?»
верные, чистая грамматика, естественные recast'ы, ~1.8 с. Весь ход ≈ 3–4 с (STT + Claude + TTS),
разбивка по шагам — в диагностике ⓘ.

**Паузы — главная сложность** (на A1 человек замолкает посреди фразы, подбирая слово). Четыре слоя:
1. **Смысл, а не только тишина.** Тишина `PAUSE_CHECK_MS` (1.5 с; вдохи посреди речи доходят до ~1 с) → запрос `mode=auto`; сервер
   отвечает `wait`, если фраза не закончена (эвристика или `complete: false` от Claude).
2. **Раннее закрытие почти бесплатно.** Заговорила, пока запрос в полёте, — он отменяется
   (`AbortController`), запись продолжается, и следующая проверка шлёт всё высказывание целиком.
   Перебила бота в первые `EARLY_BARGE_MS` (2.5 с) его ответа — ответ выбрасывается (зачёркнут в
   субтитрах, не попадает в историю), её прошлый текст уходит `prefix`'ом и склеивается с новым куском.
   Позже — обычное перебивание: бот замолкает, его реплика остаётся в истории с « —».
3. **Долгая пауза = помочь.** `STUCK_MS` (7 с) → `mode=stuck`, Claude получает маркер `[LARGA PAUSA]` и
   подсказывает слово.
4. **Видно, что бот ждёт:** кольцо вокруг шара заполняется за время паузы. Нажатие на шар во время её
   речи — «я договорила» (`mode=done`, `[TERMINÉ]`), во время речи бота — «пропустить».

Все пороги — константы `CFG` в начале скрипта `static/talk.html`; подстраиваются по живому
использованию (диагностика ⓘ показывает уровень / шум / порог и пик голоса).

**Определение голоса (VAD) — энергетическое, и тут уже была настоящая ошибка.** Во второй живой
проверке бот перебивал Ольгу *посреди обычной речи*, не на паузах. Причина: уровень фонового шума
считался средним по всем кадрам, ещё не признанным речью, — её собственный голос постепенно втекал в
«шум», порог поднимался выше голоса, и страница слышала тишину. В модели непрерывной речи
(`vad_sim`, 5×30 с) старая схема давала 15–24 ложных «договорила?», а тихий голос не слышала вовсе.
Теперь:
- **Уровень комнаты — минимум громкости за последние 2 с** (`NOISE_WINDOW_MS`): в речи между словами
  всегда есть провалы до фона, поэтому речь его не поднимает; ровный фон (телевизор, вытяжка)
  становится новым уровнем за 2 с. Пока говорит бот, не обновляется.
- Гистерезис: голос начинается с 3× уровня (`START_FACTOR`), а посреди её фразы тише части засчитываются
  с 2.2× (`KEEP_FACTOR`). Одиночный всплеск в один кадр — не голос (нужно ≥2 кадров подряд).
- Счётчик голоса не обнуляется паузами между словами (сброс только после `RUN_RESET_MS` тишины) —
  иначе перебивание бота замечалось через ~1.5 с, и ранний ответ не выбрасывался.
- **Голос, а не любой звук** (четвёртая живая проверка: пробежал кот — таймер паузы сбросился, бот
  ждал дальше). Кадр засчитывается, только если он ещё и **периодичный**: нормированная автокорреляция
  по окну 64 мс на лагах 70–320 Гц ≥ `VOICE_PERIODICITY` (0.4). У голоса есть основной тон, у шагов,
  стука и шелеста — нет. На синтетической проверке: пила (голос) 0.99, белый шум (кот) 0.09. Внутри уже
  начавшейся фразы хватает `VOICE_PERIODICITY_WEAK` (0.2) в течение `VOICE_HOLD_MS` после чёткого
  голосового кадра — иначе глухие согласные и придыхание рвали бы фразу.
- **Запасной вариант, если микрофон её не слышит** (порог периодичности не проверить без живого
  голоса): нажатие на шар в тишине начинает запись вручную, повторное — отправляет. Подсказка под шаром
  об этом говорит.
- Пока говорит бот: порог = 2.5× от измеряемой утечки его голоса в микрофон (`BARGE_ECHO_FACTOR`),
  нужно `BARGE_MS` голоса. «Ранний» ответ считается от *начала* её речи, а не от момента обнаружения.
- Страховка: ответ, пришедший, пока она говорит (`RESUME_GUARD_MS`), выбрасывается — следующая пауза
  перепроверит всё высказывание целиком.
Если снова жалоба «перебивает» — первым делом смотри в ⓘ пик голоса против порога.

**Прочее устройство:**
- `/talk` (owner-only) присылает две кнопки: Mini App (`web_app`) и «Открыть в Safari» (подписанная
  ссылка на 12 часов). Адрес — `PUBLIC_BASE_URL` или `RAILWAY_PUBLIC_DOMAIN`.
- Авторизация: `initData` Telegram (HMAC от токена бота) или подписанный токен ссылки. Оба пускают
  только владельца. Ключи OpenAI/Anthropic в браузер не попадают.
- История разговора живёт на странице и уходит с каждым ходом; `POST /talk/transcript` после каждого
  хода сохраняет её и накопленный `usage` в `voice_sessions`. По «Закончить» — итог в чат: реплики,
  прозвучавшие целевые слова (пока точное совпадение формы) и оценка цены по шагам.
- Звук на странице: захват через AudioWorklet, воспроизведение через тот же `AudioContext` (он создаётся
  в обработчике нажатия — на iOS иначе звук не пойдёт).
- `web.Application(client_max_size=10 MB)` в `bot.py` — ради WAV-загрузок (дефолт aiohttp 1 MB).

**Промпт: уроки первого живого теста (2026-09-19).** Первая версия ставила целевые слова на первое
место («меняй слово каждые 2–3 реплики») и велела «повторять её мысль правильно». Получилась анкета:
бот скакал между темами (репетитор → отдых), перед каждым вопросом повторял сказанное Ольгой, и из-за
замедленной речи говорил мучительно медленно. Теперь приоритеты такие: живой связный разговор, потом
чтобы она говорила больше бота, и только потом слова (ими можно пожертвовать). Реплика бота — реакция
(мнение, маленькая история) и в конце один уточняющий вопрос по сказанному. Правильная форма
вплетается мимоходом и только при настоящей ошибке. **Не возвращай словам первый приоритет** — ровно
это и убило флоу.

**Третья проверка: бот гнул свою тему.** Спросила, что значит слово, — получила ответ и «так вернёмся
к…». Теперь **ведёт она**: тема — то, о чём она говорит сейчас; на её вопрос бот сначала отвечает, а
уточняющий вопрос — про то, что спросила она («¿Vas mucho a la peluquería?»), а не мостик обратно
(«¿Fuiste a la peluquería en Georgia?»). Стартовая тема — только повод начать. Русское слово бот
**называет вслух** в начале реплики («"Шапка" en español es "el gorro"»; русское — кириллицей, TTS его
читает); на вопрос о значении может дать перевод одной фразой (испанское слово — латиницей).

**Русские слова посреди испанской речи.** Если она не знает слово и говорит его по-русски, Claude
в том же структурированном ответе возвращает `translations: [{ru, es}]`: отдельное слово — в словарной
форме (`el gorro`, инфинитив), целая фраза — как её сказать (`я много работаю` → `trabajo mucho`).
Голос бота остаётся полностью испанским (правка вплетается в реплику), а пара показывается на экране
плашкой под репликой и копится в `voice_sessions.found_words` (дедуп по испанскому — при склейке
высказывания то же слово приходит повторно). В итоге в чате — список «Искала по-испански» и кнопка
`talkadd:<session>:<i>` на каждое слово (до 8): нажатие отправляет испанское слово обычным путём
`_add_word()` — дедуп, недельный лимит, `explain_word`, карточка. **Автоматически в словарь ничего не
добавляется**: каждое добавление — вызов Claude, и выбор, что стоит учить, за ней. Это закрывает жалобу
№1 на сторонний бот («слова, которые он подсказал, надо запоминать и добавлять руками»).

**Память о ней между разговорами** (таблица `talk_memory`, одна строка на пользователя). Без неё бот
трижды спрашивал, сколько у неё котов: история жила только внутри сессии. Теперь по «Закончить»
`update_memory()` одним вызовом Claude переписывает список фактов из «что уже помню» + расшифровка
разговора: устойчивое про её жизнь (семья, коты с именами, работа, город, поездки, вкусы, планы),
короткими фразами по-испански, максимум `MEMORY_MAX_FACTS` (30), с объединением и исправлением
противоречий (проверено: «теперь три кота», «уже не маркетинг, а дизайн» — старые факты заменились, а
не задвоились). В инструкцию каждого хода факты идут блоком «что ты уже знаешь о ней» + правило «не
спрашивай о том, что знаешь, опирайся на это». Ошибок и слов, которые она искала, память НЕ хранит —
это не про язык, а про неё. Владельцу: `/talkmemory` — посмотреть, `/talkforget` — стереть.
Стоит это один вызов Sonnet на разговор (~цент) и не влияет на задержку: считается после конца сессии.

**Четвёртая проверка: вопросы были примитивными** («какого цвета шапка?», «часто ходишь в
парикмахерскую?»). Простой язык бот понял как простое содержание. В промпте теперь отдельный блок
«What to ask about»: язык простой, а вопрос — взрослый (опыт, мнение, причины, сравнения, выбор,
планы), ответ на 2–3 фразы; цвета, количества и вопросы с ответом в одно слово названы плохими
примерами; нужное для ответа слово бот кладёт прямо в вопрос. Стало: «¿La paella salió bien o fue un
pequeño desastre?», «¿Qué es lo peor del invierno en Moscú para ti?». **Не убирай примеры плохих
вопросов** — без них модель снова уезжает в цвета и «сколько у тебя…».

**Вспоминание против шедоуинга — почему сделано именно так** (разбор по исследованиям, 2026-09-20,
Ольга сомневалась, что сможет вспоминать слова сама). Извлечение из памяти даёт удержание лучше, чем
повтор за диктором; **неудачная попытка с немедленной подсказкой — тоже выигрыш** (errorful
generation / pretesting effect): рассогласование «что хотела сказать» и «как правильно» усиливает
внимание к подсказке. Шедоуинг силён для произношения, интонации, беглости и уверенности, но слабее
для запоминания. Поэтому очередь, а не выбор: (1) бот подводит к слову и сам его не называет;
(2) она не вспомнила (обошла, сказала по-русски, застряла) — бот даёт слово живой фразой и сразу
предлагает употребить его в своей; (3) слово остаётся в целевых и в следующий раз снова идёт без
подсказки. Карточки `/review` — отдельный канал чистого вспоминания.

**Учёт «сама / после подсказки»** (`track_word_use`, колонка `voice_sessions.word_use`): по каждому
целевому слову запоминается, кто произнёс его первым. Её текст первым → `spontaneous`, ответ бота
первым → `hinted`, а если она потом это слово употребила → `after_hint`. Итог сессии показывает три
группы. Это данные для решения, не украшение: если «сама» держится около нуля, слова берутся слишком
трудные и подсказывать надо раньше. `_word_used()` ловит точную форму плюс грубый стем для одиночных
глаголов (`hablar` → `hablé`), но не неправильные формы (`ir` → `fui`).

**Разбор после разговора** (`analyze_conversation`, колонка `voice_sessions.analysis`, отдельное
сообщение в чат после итога). Два блока, как просила Ольга: **ошибки** (слово не то, форма глагола,
род/число, артикли, предлоги, ser/estar, порядок слов) и **как сказать лучше** (то, что верно, но
плоско, плюс хотя бы одна готовая фраза-заготовка вроде `es que…`, `sobre todo`). Разбираются только
её реплики, объяснения по-русски, испанский остаётся испанским, не больше 5 ошибок и 4 улучшений.
Считается параллельно с обновлением памяти, после конца сессии, так что на разговор не влияет; сбой
разбора не должен ронять итог (проверено тестом).

**Правила против ложных придирок** — те же грабли, что в вечерней практике: она женщина, поэтому
`estoy cansada` — верно и «исправлять» нельзя; огрехи распознавания (пунктуация, значки ударения,
«э-э», повторы) не комментируются; русское слово — пробел в словаре, а не ошибка; латиноамериканский
и испанский варианты одинаково верны; «верно, но можно иначе» идёт в улучшения, а не в ошибки. На
проверочной расшифровке с ловушками (2 прогона) находились ровно четыре настоящие ошибки — *yo fue*,
*el playa*, *que es muy cerca*, *veinte y cinco* — и ни одной ложной. **Если меняешь промпт —
прогоняй на такой же расшифровке с заведомо верными местами.**

**Регион.** С компьютера Ольги OpenAI отвечает 403 `unsupported_country_region_territory` (Anthropic —
работает). На Railway оба доступны; теперь все вызовы идут с сервера, так что VPN на телефоне для
разговора больше не нужен.

**Не сделано** (сознательно, следующие шаги): нажатие на любое слово в субтитрах → в базу, разбор транскрипта Claude после сессии, недельный анализ, стриминг TTS
по предложениям (сократил бы паузу перед ответом).

**Тесты:** серверная логика хода (эвристика, `wait`/`stuck`/`done`, склейка `prefix`, авторизация,
итог) проверялась временным скриптом с заглушками STT/Claude/TTS; логика пауз страницы — в браузере на
синтетическом «голосе» (осциллятор вместо микрофона, подменённый сервер). Решения Claude
«договорила?» проверялись на реальных вызовах.

## Добавление слова голосом (все пользователи)

Добавлено 2026-09-15 по запросу одного из тестировщиков. Надиктовать слово или короткую фразу
(по-русски или по-испански) — бот показывает «🎧 Услышала: …» с кнопками «Добавить» / «Отмена»,
после подтверждения слово идёт **ровно тем же путём, что и текстовое** — `_add_word()` в `bot.py`
(вынесено из `handle_message()`): дедуп до Claude, недельный лимит, `explain_word`, карточка.

- **Маршрутизация всех голосовых — `handle_voice()`**: у владельца при активной практике *сегодняшней*
  даты → ответ практики; во всех остальных случаях → добавление слова. `get_active_practice_session()`
  фильтрует по `session_date`, иначе недоделанная вчерашняя практика перехватывала бы голосовые весь
  следующий день (дыра нашлась как раз при добавлении этой фичи).
- **Подтверждение обязательно**: одно короткое слово без контекста — самый частый случай ошибки
  распознавания, а каждое добавление — вызов Claude и минус слово из недельного лимита.
- Текст ждёт подтверждения в `context.user_data["pending_voice_word"]` с токеном (`callback_data`
  ограничен 64 байтами). Потерялся при рестарте → «запись устарела, надиктуй ещё раз».
- `stt_helper.transcribe_word()` — без `language` (иначе принудительно один язык), промпт называет оба
  языка; обрезает пунктуацию по краям, потому что дедуп сравнивает фразу точно.
- Длиннее `VOICE_WORD_MAX_CHARS = 80` — не карточка, просьба надиктовать короче.

Тест — в том же `tests/simulate_practice.py` (раздел 12).

## Известные проблемы и ограничения

1. **context.user_data эфемерно** — очередь /all, а также `review_shown` теряются при рестарте бота на Railway. Пользователь должен начать заново. Для фикса нужно хранить состояние в БД.

2. **Пропуск в предложении часто не получается сделать** — если пример не содержит точного вхождения слова (другая форма глагола, множественное число существительного и т.д.), карточка падает на уровень 2 (контекст без пропуска) или 3 (голый перевод). Это ожидаемо, не баг — см. «Типы карточек».

3. **Overdue-пул не сбрасывается автоматически** — если пользователь не заходит несколько дней, слова накапливаются в overdue. При следующем /review все придут сразу. Это намеренно.
